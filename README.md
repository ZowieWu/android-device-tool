# android-device-tool

用一条命令采完一台 Android 设备的存储与内存数据，并把过程和结果一起留下来。

## 一、它解决什么问题

**谁在受苦**：做跑机验证的测试人员。每轮跑机需要设备运行一定的时间，并检测它各方面数据的反馈，结束后要一台台设备点进去看前后数据对比，再手抄进 Excel。

**现在的人工流程，4 步**：

1. 逐条敲命令：`df -h` / `free -m` / `du -h /data`
2. 看屏幕上显示出来的数值
3. 截图，留作人工佐证
4. 把数值手抄进 Excel

**目标流程，1 步**：点一次 → 工具自动执行命令 → 自动截图 → 把截图拼接成长图 → 数值写进 Excel。

**截图不是装饰，是证据链**。数据是给整机/产品做判断用的，事后必须能回查到"当时屏幕上是什么样"。

**省下来的时间**：单台设备的采集与录入，**目标**：从 20 分钟压到 5 分钟以内。

## 三、我发现的数据坑（全部来自真实输出）

1. **单位混用**。同一个列里 G/M/K 混着出现（`2.9G` 和 `669M` 相邻），还有一格是**裸的 `0`**，没有单位。按"最后一个字符就是单位"去解析，这里就会出错。
2. **14 行里只有 1 行有用**。`df -h` 输出 14 行，只有 `/dev/block/sdb2 → /data` 能回答"设备存储满没满"。其余是：内存盘（`tmpfs` ×5）、宿主机磁盘（`/mnt/shared/*` ×4）、重复挂载（`/dev/fuse` 与 `/data/media` 是同一块 48G 分区）。
3. **模拟器会混进宿主机的盘**。`/mnt/shared/*` 那 4 行的数字是跟着 Windows C 盘在变的（前一天 124G 用 / 276G 可用，第二天 129G 用 / 271G 可用，同期实测 C 盘 128.7G 用 / 271.3G 可用）。真机上不会出现这几行，但解析层不能假设它不存在。

## 四、只采集这几样（白名单）

| 命令 | 要什么 |
|---|---|
| `df -h /data` | `/data` 的容量、已用、可用 |
| `free -m` | 内存总量、已用、可用（内存 ≠ 存储） |
| `du -h /data` | 数据目录各子目录的占用 |

白名单以外的行一律不进表，但**要记录被排除的行和原因**（不许静默丢弃）。

## 五、我的节奏

每天 1 个 commit，10 分钟起步；可以提前存、可以次日补；单日不超过 90 分钟；**连续 48 小时仓库里没有新东西 = 断了**。

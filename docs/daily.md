## 2026-10-23（五）—— 使用率与阈值判断

| 新增的东西 | 作用 | 解决了什么问题 | 用到了什么 |
|---|---|---|---|
| `samples/df-k-data.txt` | `df -k /data` 的真实输出 | 算使用率需要 total/used，之前只有 du 的目录大小 | `-k` 让输出是纯数字；`>` 与 `2>` 分开收 |
| `usage(row)` | 从 df 一行算**真实**使用率 | **`Use%` 列是取整的**（显示 1%，真实 0.75%） | 按位置取值、除法、`round`、`if total else 0.0` |
| `judge(pct, rated)` | 和"项目额定百分比"比，给人话结论 | 模板要"是否超过额定值、超了标红" | 返回字符串、`{:.2f}` 与 `{:g}` 的取舍、**边界定义** |
| `--rated` 参数 | 额定值可配（默认 80） | 每个项目额定值不同 | `sys.argv` 解析 |
| 接进主流程 | 采集后自动打印"使用率 + 是否超额定" | 之前只有磁盘明细，没有"满没满" | **复用 `parse_df()`**（`df -k` 与 `df -h` 同构，6 字段） |

**坑：**
1. **`df <路径>` 的 `Mounted on` 不可信**：`/dev/block/sdb2` 在 `/proc/mounts` 里有 **11 条**挂载记录，`df -k /data` 返回的挂载点是 `/system/vendor/lib/arm/cpuinfo`（一个从 /data bind 出去的文件）。**判断"这行是不是 /data"不能看这一列。**
2. **`Use%` 是取整的**：显示 `1%`，真实 `0.75%`——**差 33%**。判断必须自己算 `used/total`。
3. **显示精度必须和判断精度一致**：`{rated:.0f}` 把 0.5 显示成 `0%`，于是出现"超额定（0.75% > 额定 0%）"——**同一类 bug 在 `humanize` 之后又出现一次**，改用 `:g`。
4. **`IndentationError` 会让编辑器到处画红线**：8 格 vs 4 格的缩进错误，报错只指一处，但红波浪线是**级联假象**。判据：`python -c "import parse"` 看第一处语法错误。

**一句话：`df` 的输出里有两列不能信：`Mounted on` 和 `Use%`——"工具给的视图"和"底层事实"不是一回事。**

## 2026-10-27（二）—— 判断层：prompt 与最小 LLM 调用

| 新增的东西 | 作用 | 解决了什么问题 | 用到了什么 |
|---|---|---|---|
| `build_prompt()` | 把"增长最大的 3 条 + 使用率 + 内存"拼成一段给模型看的 prompt | 模型不会猜你的意图，你得把"判断什么、输出什么"写死 | 列表推导、`sort(key=...)`、f-string、`"\n".join` |
| `call_llm()` | 调 DeepSeek（OpenAI 兼容接口），拿回一句话 | 人肉判断"这次跑机有没有异常"太主观 | **标准库 `urllib`**（不引依赖）、`os.environ`、`json`、`raise RuntimeError` |
| `--llm` 开关 | 默认**干跑只打印 prompt**，加 `--llm` 才真发 | **没 key 也能开发和测试**——外部依赖不该阻塞工作 | `sys.argv`、依赖隔离、`try/except RuntimeError` |
| 2 条 `build_prompt` 测试 | 关键事实必须在、长度有上限、`pct=None` 不能崩 | prompt 的**内容**也要有测试 | `in` 断言、长度断言、`None` 边界 |

**坑：**
1. **按增长%排序会挑出垃圾**：`1K→2K` 是 `+100%`，但毫无影响 → **改按绝对增长量排**（真正让存储满的是绝对量）。
2. **全 0 增长时"最大的 3 条"是随机的**，模型很可能开始编异常 → 加第 3 条约束："全接近 0 就说「无明显异常」，不要编造原因"。
3. **没有 API key 也能开发**：把"调模型"隔离成一个可跳过的步骤（干跑 → `--llm`）。这和 `--offline` 是同一个思路。
4. **key 绝不进代码/仓库**（仓库是 public）：只从环境变量读，没有就报错退出。

**一句话：模型的默认行为是"找到点什么"**——不明确告诉它"没事就说没事"，它就会给你一个像样的错误结论。

**一句话：文档写「功能」，不如写「决定 + 它堵的失败」**——前者是说明书，后者是经验。

## 2026-10-28（三，第二格）—— 把清单从 7 条扩到 28 条

| 新增的东西 | 作用 | 解决了什么问题 | 用到了什么 |
|---|---|---|---|
| `paths.example.txt` 扩到 28 条 | 命中 **4/7 → 25/28** | **7 条的清单，工具和手工一样快**——杠杆 = 清单长度 × 采集次数 | 从 1732 行真实数据里按大小挑"稳定的"路径 |
| 注释写清 4 条规则 | 什么能进清单、什么绝对不能 | 怕以后自己（或别人）把混淆目录写进去 | `~~xxxx` 会变；`/data/data` 与 `/data/user/0` 同源 |

**坑：**
1. **`~~xxxx` 混淆目录每次安装都变**，写进清单今天能命中、明天就命中不了 → **只能写包名（`com.xxx`）**。
2. **`/data/data` 与 `/data/user/0` 是同一个目录**（实测都是 13844K），两个都列会出现两行一样的数字。
3. **清单变了，旧快照就不能直接比**：新清单 28 条、旧 before 只有 4 条 → 增长表大半是 `—`，**而工具什么都没说**。→ 演示必须先跑一次 `before`；（改进想法：在快照里记"清单指纹"，对比前校验）

**一句话：工具的杠杆 = 清单长度 × 采集次数**——清单只有 7 条时，人工敲 7 次也就完了，工具根本没有存在的意义。

## 2026-10-28（三，第三格）—— 主动砍掉演示录屏

| 新增的东西 | 作用 | 解决了什么问题 | 用到了什么 |
|---|---|---|---|
| README「不做的东西」一节 | 把两项砍掉的交付物**写下来**，附理由 | 待办清单里躺着"永远不做"的项，会一直啃人 | "决定不做" ≠ "还没做" |
| 工作台笔记里把 4f 标成 ❌ 主动砍掉 | 验收从 6 条变成 **5 条达成 + 1 条放弃** | 诚实的进度优于好看的进度 | 取舍要留痕 |
| 下一步转向「怎么把项目说清楚」 | 让最后一点力气花在**表达**上 | 代码已够，价值卡在"能不能被看懂" | 交付物意识的转向 |

**坑：**
1. **长录屏的边际价值很低**：4 分钟的视频没人看完，一屏终端输出反而更清楚；**文字说明可控、可裁剪、能追问**。
2. **录屏体积**：Game Bar 录 4 分钟就是 77MB——**任何几十 MB 的视频都不该进仓库**。
3. **"没做"和"决定不做"是两件事**：前者是欠债（一直啃你），后者是取舍（让你轻装）。

**一句话：把「没做」改成「决定不做」，清单才会变短，而不是变脏。**

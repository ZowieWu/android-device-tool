# android-device-tool

用一条命令采一台 Android 设备的**磁盘、内存、使用率**，按清单报出**命中率**和**缺失项**，跑两次还能算出**增长%**并写成 Excel——让人知道这份数据**能不能被信任**。

## 一、它解决什么问题

**谁在受苦**：做跑机验证的测试人员。每轮跑机结束后，要一台台设备点进去看数据、截图、手抄进 Excel，再算"跑机前 vs 跑机后"的增长。

**现在的人工流程**

1. 逐条敲命令（`du /data`、`df`、`free`）→ 2. 看屏幕上的数 → 3. 截图留证 → 4. 手抄进 Excel 再算增长

**现在工具能做的**：一条命令采完 → 自动和"跑机前"对比 → 出增长% + 内存/使用率 → 写成 xlsx。

**目标**：单台设备从 20 分钟压到 5 分钟以内，人只负责判断。

## 三、我发现的数据坑（全部来自真实输出）

1. **单位不要靠解析救**。`du /data` 默认输出第一列就是纯数字（单位 K）；**别加 `-h`**——`-h` 四舍五入，算增长% 会错（`1.2M → 1.3M` 可能是 +1%，也可能是 +15%）。
2. **行数远多于需要**。`du /data` 一次 **1732 行**，清单只有几十条 → "按清单匹配"不是优化，是必需。
3. **`df` 的输出更脏**。14 行里只有 1 行跟 `/data` 有关；其余是内存盘（`tmpfs`）、宿主机的 C 盘（`/mnt/shared/*`）、同一分区的重复挂载（`/dev/fuse` 与 `/data/media`）。
4. **路径写法不统一**。`du` 输出带前导 `/`，而内部清单不带 → **必须归一化，否则一条都匹配不上，而且不报错**。
5. **每一行末尾都有 `\n`**。读清单不 `strip()`，就是"命中 0/N"，同样不报错。
6. **权限错误有两种**。整个目录读不了 → 命令直接失败（安全）；**部分子目录读不了 → 命令照常跑完、数字偏小、不报警**（最危险）。
7. **`df <路径>` 的 `Mounted on` 不可信**。同一设备有多个挂载点时（bind mount），它可能返回另一条——`df -k /data` 会显示成 `/system/vendor/lib/arm/cpuinfo`。**判断"这行是不是 /data"不能看这一列。**
8. **`Use%` 列是取整的**。显示 `1%`，真实是 `0.75%`（差 33%）→ **要精确值就自己算 `used/total`**。
9. **Android 的 `free` 不是 Linux 的 `free`**。它是 **4 行**（多一行 `-/+ buffers/cache`）、**没有 `available`**、列名是 `buffers` → **按行首标签认行，别按行号，也别照 Linux 的列名写。**

## 四、采什么由清单决定

采集范围不写在代码里，写在**外部清单文件**（示例：`paths.example.txt`）：

- 清单里的路径才进表；不在清单里的，一律不进
- 未命中的路径必须**列出来**，不许静默丢弃
- 真实清单属于内部资料，**不进这个仓库**

> 工具只输出"清单里有、数据里没找到"的**事实**；判断那是"环境差异"还是"清单写错"，是人的事。

## 五、两条硬规则（都踩过）

1. **缺数据不许冒充**：拿不到就写 `None`/空，**不写 0**——`0` 会被当成真实数据算进占比。
2. **判断和显示必须同精度**：判断用 `0.5`、显示成 `0%`，就会出现"超额定（0.75% > 额定 0%）"。格式化时用 `:g` 这类不丢信息的写法。

## 六、判断层（LLM）：让模型说一句人话

**默认不调模型**（干跑）：只把"准备发出去的内容"打印出来，不联网、不花钱。加 `--llm` 才真发。

```bat
setx DEEPSEEK_API_KEY "sk-xxxx"                  :: 一次，重开终端生效；代码只读环境变量
python main.py --offline --stage after           :: 干跑：打印 prompt
python main.py --offline --stage after --llm     :: 真发：最后多一行 [模型判断]
```

**prompt 有 6 个设计决定，每一条都是为了堵一次具体的失败：**

| # | 决定 | 堵的是什么 |
|---|---|---|
| 1 | 只给增长最大的 3 条 | 几十行塞进去，模型会"平均用力"，重点被淹没 |
| 2 | 按**绝对增长量**排序，不按百分比 | `1K→2K` 是 +100%，但对设备毫无影响 |
| 3 | 缺数据写"未知"，不写 `0` | 写 `0`，模型会去分析一个假数字 |
| 4 | 要求"**只输出一句话**" | 不约束就给三段小作文，没法直接进表 |
| 5 | 写清"**不要做什么**" | "不要复述数据"比"请简洁"有效十倍 |
| 6 | 全接近 0 时明确说"无明显异常，不要编造" | **模型的默认行为是"找到点什么"** |

**实测（2026-10-27）**：真实数据全是 `+0.0%` 时，模型回的就是——

> `无明显异常，建议保持当前跑机配置并继续观察。`

**这不是它聪明，是第 6 条约束在起作用。**没有它，模型大概率会复述一遍数据再加一句"建议关注"。

> **⚠️ 合规提醒**：把内部路径/设备数据发给外部 API 之前，先确认公司政策。
> 代码支持"只干跑、不发"，去掉 `--llm` 即可——**这也是"外部依赖要能跳过"的实际好处。**

## 八、怎么跑

```bat
:: 前置：设备必须能读 /data（已授权的测试设备，或开了 root 的模拟器）
:: 模拟器上需要先执行一次：D:\leidian\LDPlayer14\adb.exe root

python main.py --stage before      :: 跑机前采一次，存快照
python main.py --stage after       :: 跑机后采一次 → 自动对比 → 增长% + xlsx
python main.py --rated 80          :: 项目额定百分比（默认 80；等于额定值不算超标）
python main.py --offline           :: 不连设备，用 samples/ 里的三份样本
python -m pytest -q                :: 跑测试
```

**产物位置**：`out/<串号>/<日期>-<阶段>.json`（快照）、`out/<串号>/<日期>.xlsx`（增长表 + 内存/使用率）。

**开发环境**：Windows + 雷电模拟器 14，通过 adb 连接。
**样本与出处**：见 `samples/README.md`（采集时间、采集身份、有无权限错误）。

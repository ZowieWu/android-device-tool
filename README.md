# android-device-tool

用一条命令采一台 Android 设备的存储数据，并按清单报出**命中率**和**缺失项**——让人知道这份数据能不能被信任。

## 一、它解决什么问题

**谁在受苦**：做跑机验证的测试人员。每轮跑机结束后，要一台台设备点进去看数据，记下来，再手抄进 Excel，还要截图留证。

**现在的人工流程**

1. 逐条敲命令（`du /data`、`df`、`free` 之类）
2. 看屏幕上显示的数值
3. 截图，留作人工佐证
4. 把数值手抄进 Excel，再算"跑机前 vs 跑机后"的增长

**目标**：一条命令完成采集 → 数值进表 + 截图留证，人只负责判断。

**省下来的时间**：单台设备的采集与录入，**目标**从 20 分钟压到 5 分钟以内。

## 三、我发现的数据坑（全部来自真实输出）

1. **单位不要靠解析救**。`du /data` 默认输出的第一列就是纯数字（单位 K），没有 `G`/`M` 字母。**用默认输出，别加 `-h`**——`-h` 会四舍五入，后面算增长% 会错（`1.2M → 1.3M` 可能是 +1%，也可能是 +15%）。
2. **行数远多于需要**。`du /data` 一次输出 **1732 行**，而清单只有几十条。所以"按清单匹配"不是优化，是必需。
3. **`df` 的输出更脏**。14 行里只有 1 行（`/dev/block/sdb2 → /data`）能回答"设备存储满没满"；其余是内存盘（`tmpfs`）、宿主机的 C 盘（`/mnt/shared/*`）、同一分区的重复挂载（`/dev/fuse` 与 `/data/media`）。
4. **路径写法不统一**。`du` 输出带前导 `/`（`/data/fonts`），而内部表格的清单不带（`data/fonts`）→ 匹配前必须归一化，**否则一条都匹配不上，而且不会报错**。
5. **每一行末尾都有 `\n`**。读清单不 `strip()`，就永远匹配不上——结果是"命中 0/N"，同样不报错。
6. **权限错误有两种**。整个目录读不了 → 命令直接失败（安全）；**部分子目录读不了 → 命令照常跑完、数字偏小、不报警**（最危险）。

## 四、采什么由清单决定

采集范围不写在代码里，写在一个**外部清单文件**里（示例：`paths.example.txt`）：

- 清单里的路径才进表；不在清单里的，一律不进
- 未命中的路径必须**列出来**，不许静默丢弃
- 真实清单属于内部资料，**不进这个仓库**

> 工具只输出"清单里有、数据里没找到"的**事实**；判断那是"环境差异"还是"清单写错"，是人的事。

## 六、怎么跑

```bat
:: 前置：设备必须能读 /data（已授权的测试设备，或开了 root 的模拟器）
:: 模拟器上需要先执行一次：D:\leidian\LDPlayer14\adb.exe root

python main.py              :: 连设备采集
python main.py --offline    :: 不连设备，用 samples/du-data.txt
python -m pytest -q         :: 跑测试
```

**开发环境**：Windows + 雷电模拟器 14（Android 模拟器），通过 adb 连接。
**样本与出处**：见 `samples/README.md`（含采集时间、采集身份、有无权限错误）。
